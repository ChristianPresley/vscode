# MCP end-to-end tests (llama.cpp, WSL Containers)

End-to-end tests of the MCP client of this VS Code fork as a user gets it: the fork is built as a Linux `.deb`, installed into a fresh WSL container and started headless, and talks to MCP servers over every transport (stdio, Streamable HTTP, legacy HTTP+SSE, gRPC tunnel and typed, gRPC over TLS) and both protocol revisions (2026-07-28 and 2025-11-25). A real language model served by [llama.cpp](https://github.com/ggml-org/llama.cpp) (Qwen3 8B, in its own container) is the chat model: it answers MRTR and legacy sampling requests, and in the agent tests it picks the tool call (over stdio, the gRPC tunnel and typed bindings, and through the gateway over HTTP and gRPC). Every other test calls the tool it needs directly with `vscode.lm.invokeTool`, so the result does not depend on the model's choice. The E2E extension also contributes the chat participant `@e2e` (see "The chat participant"), so MCP tool calls run from the chat view without a Copilot sign-in. A second, Playwright-driven pass answers the elicitation and OAuth UI and takes screenshots for visual checks, including MCP tool calls from the chat view through `@e2e`. A last phase applies an MCP allow list through a real enterprise policy (`/etc/vscode/policy.json` inside the test container) and checks what VS Code allows and denies under it (see "Enterprise policy phase").

Everything is TypeScript (the extension is compiled with `tsc` inside the container; the scripts run with Node's type stripping) plus PowerShell/bash drivers. Nothing here is part of the product build.

## Prerequisites

- Windows 11 with **WSL 3** and the WSL Containers CLI `C:\Program Files\WSL\wslc.exe` (Docker-compatible; Docker or Podman are not needed).
- PowerShell 7 (`pwsh`) for the drivers; Node.js 24 on the host only for `run-mutations.ps1` and `runner/mutations.ts`.
- An NVIDIA GPU for `llama.cpp:server-cuda` (an RTX 5090 runs the model at 90-160 tokens/s; 8 GB of VRAM are enough). Without one, pass `-Cpu` (the CPU image `ghcr.io/ggml-org/llama.cpp:server`; much slower, raise the timeouts if needed).
- About 16 GB of memory for the container VM during the product build (llama-e2e is stopped while it runs) and 25 GB of disk (images, the `vscode-e2e-work` volume, the model).
- The model, `Qwen3-8B-Q4_K_M.gguf` (5.0 GB), in `.build\e2e-models\`:

  ```powershell
  New-Item -ItemType Directory -Force .build\e2e-models | Out-Null
  Invoke-WebRequest -Uri https://huggingface.co/Qwen/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf -OutFile .build\e2e-models\Qwen3-8B-Q4_K_M.gguf
  ```

- The zig-sdk repository (the 2026-07-28 conformance server) at `C:\repos\zig-sdk` (`-ZigSdk` to change it); its servers are built into the volume on the first run.
- Network access from the containers on the first run (Ubuntu packages, Node.js, npm, the Chromium sysroots of the deb packaging, the container images).

## Running

From the repository root:

```powershell
pwsh -File test\mcp-e2e\run-e2e.ps1                          # build the .deb of the checked-out branch, then run everything
pwsh -File test\mcp-e2e\run-e2e.ps1 -SkipBuild               # reuse the newest .deb in .build\e2e
pwsh -File test\mcp-e2e\run-e2e.ps1 -SkipBuild -Repeat 3 -RunId final       # the strict 3x run
pwsh -File test\mcp-e2e\run-e2e.ps1 -Deb .build\e2e-keep\m8-6201d830320.deb -SkipUi -Only 'gRPC soak'
pwsh -File test\mcp-e2e\run-e2e.ps1 -SkipBuild -Only policy  # only the enterprise policy phase
pwsh -File test\mcp-e2e\run-mutations.ps1                    # every mutation run (see "Mutation runs")
```

```sh
test/mcp-e2e/run-e2e.sh --skip-build --repeat 3              # Git Bash: the same options, mapped onto run-e2e.ps1
```

| Option | Meaning |
| --- | --- |
| `-Branch <name>` | The branch to build. The default is the checked-out branch. Only **committed** state is built: the repository is mounted read-only and cloned inside the container. |
| `-SkipBuild` | Use the newest `.deb` of `.build\e2e` instead of building. |
| `-Deb <path>` | Test this package instead of the newest `.deb` of `.build\e2e` (implies `-SkipBuild`). A path under `.build\e2e` is used from the results mount; any other file is mounted read-only. |
| `-Repeat <n>` | Run the suite `n` times (1-20), each in a fresh container with its own run id `<run id>-r<i>`, then write `runs\<run id>-aggregate.md` and `.json`. Strict: the run passes only when every repetition passed, on the same installed commit and the same suite hash. |
| `-Mutate <names>` | Apply mutations of `runner/mutations.ts` (comma-separated); each must make its tests fail (see "Mutation runs"). The summary names them in its first lines. |
| `-SkipApi`, `-SkipUi` | Skip the API suite (extension tests) or the UI suite (Playwright). `-SkipUi` also skips the enterprise policy phase, which is Playwright-driven. |
| `-SkipPolicy` | Skip the enterprise policy phase only. |
| `-AllowFail <groups>` | Comma-separated test groups whose failures are reported as `FAIL (allowed)` without failing the run, for example `grpc` on a build without the gRPC transport; `visual` does the same for the screenshot checks. |
| `-Only <substrings>` | Run only the tests whose name contains one of the comma-separated substrings (UI scenarios also match by their id; `screenshots` selects every screenshot section of the UI suite, `shot:<section>` one of them, for example `shot:chat app`; the section names are those of the `section(...)` calls in `ui/visual.ts`, and `shot:accounts` needs the `oauth` scenario in the same run). The entry `policy` selects the enterprise policy phase (which runs whole; without `-Only` it runs too), and `-Only policy` alone runs only that phase: no test of the API or UI suite has "policy" in its name, so both are skipped (`shot:policy` is the UI section 21, not this phase). |
| `-RunId <id>` | The name of the results folder (default: a UTC timestamp). |
| `-Cpu` | Start llama.cpp on the CPU. |
| `-RebuildZig`, `-ZigSdk <path>`, `-ZigBranch <b>` | Rebuild the zig-sdk servers (by default only when they are missing from the volume). `-ZigBranch` takes a branch or a tag; the default is the release `v0.6.0`. |
| `-KeepLlamaDuringBuild` | Do not stop `llama-e2e` while the product builds. |

The driver exits non-zero when any test fails or any screenshot fails its DOM checks (1: a check that does not hold, a screenshot section that threw, or a screenshot whose UI never showed), or when a suite produced no results (2). A test that skips although this build is expected to support what it tests fails (see "Expectation flags").

**Results**: `.build\e2e\runs\<run id>\`:

- `summary.md`, which starts with the provenance of the run: the installed commit (from the package's `product.json`) and its date, the package file with its size and SHA-256, whether `build-info.json` describes that package, the SHA-256 of the content of `test/mcp-e2e` as the container saw it (every file except `node_modules` and `out`, with the file count), the same hash of `test/mcp-e2e` as committed at the installed commit (from the git blobs of the build clone) and whether the two are equal ("suite matches commit": only such a run can be reproduced from the commit), the HEAD of the checkout the suite was mounted from and whether `test/mcp-e2e` had uncommitted changes there, what this build is expected to support, and the mutations, if any; then one row per test and per screenshot. `provenance.json` has the same data (`runner/provenance.ts`: `suite`, `committedSuite`, `suiteMatchesCommit`, `suiteCheckout`). Both hashes turn CRLF into LF first, so a Windows checkout (CRLF in the working tree, LF in the blobs) hashes like its commit; hashes recorded before this normalization (runs up to final-e094-r3) are not comparable with later ones.
- `api\api-results.json`, `ui\ui-results.json` and `policy\policy-results.json` (the tool calls, answers, details and UI traces of every test; the policy phase also keeps its `policy.json`, `mcp.json` and `servers.json` in `policy\`, and its driver log in `policy-driver.log`), `api\llama-requests.jsonl` (every request the provider sent to llama.cpp), `api\agent-transcripts.jsonl`, `api\chat-requests.jsonl` (`ui\` for the UI suite: every request the `@e2e` chat participant handled, with its tool calls and whether it carried a `toolInvocationToken`).
- The workbench logs of the runs (`logs-api\`, `logs-ui\`, `logs-policy\`, including the `mcpServer.*.log` file of every MCP server) and the `mcp.json`/`settings.json` of the run.
- `servers\`: the logs of the network servers and fixtures: `<label>.wire.jsonl` for every server behind `runner/grpc-log-proxy.ts` (every gRPC call that reached it, the TLS handshakes and the RST_STREAM/GOAWAY frames), `<label>.http.jsonl` for every server behind `runner/http-fault-proxy.ts` (every HTTP request with its method, MCP headers, JSON-RPC methods, status and the fault or mutation applied), `<label>.oauth.jsonl` for every OAuth fixture (every request with what it checked), `oauth-browser.jsonl` (what the stand-in browser followed), `run-suite.log`.
- With `-Repeat`: `runs\<run id>-aggregate.md`/`.json`: the installed commit, the suite hash, the committed suite hash and "suite matches commit" (yes only when every repetition ran the committed suite; also a column per run), one row per test with its result in every repetition and a stability column, and the verdict.

**Screenshots**: `.build\visual-verification\` holds those of the latest run and `runs\<run id>\screenshots\` those of each run (see [visual-verification.md](visual-verification.md)); a screenshot section that throws leaves `zz-error-<section>.png`, a scenario whose UI stalls for 30 s `zz-stall-<scenario>-<n>.png`, a part of the policy phase that throws `zz-error-policy-<part>.png`. The policy phase adds its screenshots (27 to 27c) to those of the UI suite; when the UI suite does not run, the folder holds only the policy phase's.

## What runs

`run-e2e.ps1` ensures the images (`vscode-mcp-build:latest` from `containers/Dockerfile.base`, `vscode-mcp-build:2` from `containers/Dockerfile.builder`), the network `vscode-e2e-net` and the volume `vscode-e2e-work`; builds the `.deb` (`containers/build-vscode.ps1`, unless `-SkipBuild` or `-Deb`), the zig-sdk servers (`containers/build-zig-sdk.ps1`) and starts `llama-e2e` (`containers/start-llama.ps1`); then runs `containers/run-suite.sh` in a fresh container `vscode-e2e-test` on `vscode-e2e-net` (once per repetition), which

1. installs the `.deb` (`E2E_DEB`, or the newest one) with apt, installs `tools/package-lock.json` into `/work/e2e-tools` (Playwright and `@modelcontextprotocol/server-everything`, cached in the volume), and compiles `extension/` against the `vscode.d.ts` of the commit the `.deb` was built from;
2. writes `provenance.json` (`runner/provenance.ts`) and from it the expectation flags `MCP_E2E_EXPECT_GATEWAY_GRPC` and `MCP_E2E_EXPECT_GATEWAY_RATE_LIMITS`;
3. writes the profile (`runner/prepare-profile.ts`): the user-level `mcp.json` with the servers of `config/servers.json`, `settings.json` (`chat.tools.global.autoApprove`, `chat.mcp.serverSampling` allowing `llamacpp/qwen3-8b` in and outside chat for every server, `chat.mcp.autostart`, discovery of other applications' configurations off, in-DOM dialogs, `workbench.externalBrowser` = the stand-in browser below) and the one-time opt-in of the global auto-approval in the application storage; it also generates the throw-away CA of the `grpcs://` servers (`runner/test-ca.ts`, openssl: `/tmp/e2e/tls/ca.pem` plus a `localhost` server certificate and key, valid two days, never in the repository or the results; `tls.ca` in `mcp.json` and in the API definition point at `ca.pem`, the extension gets the folder as `MCP_E2E_TLS_DIR`) and writes `/tmp/e2e/bin/mcp-e2e-browser`, a wrapper of `runner/oauth-browser.ts`;
4. starts the network servers and fixtures (`runner/start-servers.ts`; the zig servers listen on 127.0.0.1 only, so they run in the VS Code container), see below;
5. runs the **API suite**: `code-oss --extensionDevelopmentPath=extension --extensionTestsPath=extension/out/suite/index.js` under `xvfb-run` (1600x1000), `--log debug` so that the MCP logs carry every JSON-RPC message;
6. restarts the network servers and runs the **UI suite**: `ui/visual.ts` launches `/usr/share/code-oss/code-oss` with Playwright's `_electron.launch` (same flags, a fresh copy of the same profile) with the extension in UI mode;
7. restarts the network servers and runs the **enterprise policy phase**: `ui/policy.ts` writes `/etc/vscode/policy.json` and launches the installed binary once more the same way, with its own copy of the profile reduced to three servers (see "Enterprise policy phase"); it removes the policy file afterwards;
8. copies everything out and prints the summary (`runner/summarize.ts`).

### Fixtures (`runner/`)

The servers of the run log little or nothing about what VS Code sent, and none of them produces most of the error paths, so the suite puts its own fixtures in front of them. Every fixture writes one JSON line per event into `servers\`.

- `grpc-log-proxy.ts`: an HTTP/2 proxy (TCP or TLS front end, relayed to a Node `http2` server that forwards each call) that records every gRPC call (connection, HTTP/2 stream id, path, MCP metadata including `grpc-timeout` and `mcp-param-*`, the JSON-RPC methods of a tunnel `Call`, `grpc-status`, `mcp-error-code` and whether `mcp-error-bin` was present), every RST_STREAM and GOAWAY frame either side sent, and every TLS handshake. Options per server (`config/servers.json`, `grpcLogProxy`): `refuseTunnel` answers the tunnel itself with a bare UNIMPLEMENTED (a typed-only server); `tls` terminates TLS with the run's certificate; `resetLimit` sets the rapid-reset bucket of the Node `http2` server; `mangle` rewrites the mirrored `mcp-name` metadata of a tool's `tools/call` (`<tool>=<value>[:once]`), so the zig server answers -32020; `hold` delays a tool's `tools/call` by some milliseconds before forwarding it.
- `http-fault-proxy.ts`: a Streamable HTTP proxy that records every request (`<label>.http.jsonl`) and, per server (`httpProxy.faults`), injects 2026-07-28 error paths for named tools: `missing-capability:<tool>` (HTTP 400, -32021 for `elicitation.url`), `result-type:<tool>=<v>` (the answer's `resultType` replaced), `output-schema-mismatch:<tool>` and `output-schema-match:<tool>` (the tool listed with an `outputSchema`, its answer given a `structuredContent` that does not or does match), `version-same:<tool>` (400, -32022 offering only 2026-07-28), `version-legacy:<tool>` (400, -32022 offering only 2025-11-25; the proxy then serves the 2025-11-25 handshake itself and bridges the following requests to the 2026-07-28 server), `empty-cursor` (every `tools/list` split in two pages, the first with `nextCursor: ""`), `input-required-url:<tool>` (every call without `inputResponses` and `requestState` is answered with `input_required` holding one URL-mode `elicitation/create` under the key `consent`: `url` `https://url-elicitation.mcp-e2e.test/consent?id=<round>` (no `elicitationId`: the 2026-07-28 URL params have none), a message naming the tool and the round, and a `requestState` the proxy signs with HMAC-SHA256; 400 with -32021 when the request's `_meta` client capabilities lack `elicitation.url`. The retry with that `requestState` and `inputResponses.consent` `accept` is forwarded without both fields, so the tool's own result comes back; `decline` or `cancel` is answered with "URL elicitation <action>: <tool> was not run"; a missing or wrong `requestState`, or no valid `inputResponses.consent`, gets 400 with -32602. The log has the round's `url` and `requestState`, and the retry's `inputResponses` and `requestState`). It also applies the HTTP mutations of `runner/mutations.ts`.
- `oauth-fixture.ts`: the protected resource (`/mcp`: 401 with `WWW-Authenticate: Bearer resource_metadata="<the PRM URL>", scope="mcp:tools"` without a valid token; with one, the request is forwarded) and the authorization server (RFC 9728 and RFC 8414 metadata with `code_challenge_methods_supported: ["S256"]` and `authorization_response_iss_parameter_supported: true`, dynamic client registration, `/authorize` that approves at once with a 302 to the loopback redirect URI carrying `code`, `state` and `iss`, and `/token` that checks the code, client, redirect URI, the PKCE verifier against the S256 challenge and the RFC 8707 `resource`; a token is valid only for its resource). Options: the authorization server on its own port and with a path issuer (`asPort`, `asPath`), the PRM at a custom path that only the challenge names (`prmPath`), `issMode` `wrong` (an `iss` that is not the issuer) or `omit` (no `iss`), and `grpcPort`: an h2c front for a gRPC server that answers a call without a valid token trailers-only with `grpc-status: 16` and `www-authenticate`, and forwards authorized calls (the PRM `resource` is then `https://127.0.0.1:<grpcPort>/`).
- `oauth-browser.ts`: the "web browser" of the container (`workbench.externalBrowser`): for an authorization URL it does what a user who approves does: it requests the URL and follows the redirect to VS Code's loopback redirect URI. It only ever fetches loopback URLs; any other URL (the URL-mode elicitation of the UI suite) is recorded with its origin, path and query (`open`, `followed: false`) and not fetched.

### The E2E extension (`extension/`)

- `llamaProvider.ts`: `vscode.lm.registerLanguageModelChatProvider('llamacpp', ...)` (contribution `languageModelChatProviders`), backed by llama.cpp's `/v1/chat/completions`: VS Code tool definitions become OpenAI `tools`, `tool_calls` become `LanguageModelToolCallPart`s, `LanguageModelToolResultPart`s become `role: tool` messages (images and resource links are described in text for the text-only model). Qwen3's reasoning is switched off with `chat_template_kwargs.enable_thinking: false` (any leftover `<think>` block is stripped); `temperature: 0` and a fixed seed keep runs repeatable. Every request is logged to `llama-requests.jsonl`.
- `agent.ts`: the agent loop of the agent tests and of `@e2e /ask`: the task and the offered tools go to `vscode.lm.selectChatModels({ vendor: 'llamacpp' })`; the first turn requires a tool call, the model picks which; the results go back until the model answers. #### Enterprise policy phase (`ui/policy.ts`)

VS Code on Linux reads its policies from `/etc/vscode/policy.json`, for every product (`src/vs/code/electron-main/main.ts` registers `FilePolicyService` for `LINUX_SYSTEM_POLICY_FILE_PATH`). The phase runs last in the test container, after the API and UI suites, so that nothing else sees the policy, and writes that file with `ChatAllowedMcpServers`, the policy of `chat.mcp.allowedServers`:

```json
{
	"ChatAllowedMcpServers": "[{\"serverName\":\"zig-http\"},{\"serverUrl\":\"grpcs://localhost:50056\"}]"
}
```

The value is the allow list as a JSON **string**: a policy value is a string, a number or a boolean, the policy of an array setting has the type `string` (`configurations.ts` `toPolicyDefinitionType`), and `PolicyConfiguration` parses the JSON in it for a setting that cannot be a string, as for the Windows registry and macOS profiles (the Linux template `build/lib/policies` generates has `""` for such a policy). `FilePolicyService` would also pass a raw array through, but that is not the declared type. The `serverUrl` is the `url` of zig-grpcs-insecure in the run's `mcp.json`, which matches the URL VS Code checks (`launch.uri.toString(true)`) exactly.

The phase launches VS Code once more with Playwright (`launch` of `ui/visual.ts`) with its own copy of the profile, whose user `mcp.json` holds only three servers, and the E2E extension, which here defines no API servers (`MCP_E2E_SERVERS`: `config/servers.json` reduced to the three) and starts no server itself (`MCP_E2E_START_SERVERS=0`: the driver starts each one with `workbench.mcp.startServer`). Under that policy:

- `zig-http`, allowed by its name, runs and lists its tools, and its proxy gets VS Code's requests;
- `zig-stdio`, not in the list, is in the Error state with "This Model Context Protocol server is not in the list of servers allowed by your organization. ..." (`allowedMcpServersService.ts`) and is never launched (no connection state in its MCP log);
- `zig-grpcs-insecure`, allowed by its `grpcs://` URL, has `tls.insecure`, which is denied while the allow list comes from a policy (`mainThreadMcp.ts` `_checkInsecureGrpc`, `mcp.grpc.insecureDenied`, through `$checkMcpServerAllowed` before the first gRPC call): the Error state with "The MCP server 'zig-grpcs-insecure' turns off TLS certificate verification (`tls.insecure`), which is not allowed while your organization manages the allowed MCP servers.", no "TLS certificate verification is turned off ..." warning, and the TLS front end of zig-grpcs (`zig-grpcs.wire.jsonl`) sees no connection and no handshake from the window;
- the value comes from the policy: the extension API's `inspect` of `chat.mcp.allowedServers` reports the allow list as `defaultValue` (`extHostConfiguration.ts` reports the policy value there; the registered default is `null`) with no user, workspace or folder value, and the user `settings.json` does not set it; Developer: Policy Diagnostics lists the setting under "Applied Policy" with the policy `ChatAllowedMcpServers` and the source Device (the policy file).

The tests are decided once the window is closed, from the List Servers quick pick, the window's MCP logs, the logs of the network servers and the configuration the E2E extension's control server reports (`GET /config`, `GET /documents` for the Policy Diagnostics report); the screenshots 27 to 27c have their own DOM checks (visual-verification.md). A policy file that exists before the phase is left alone and the phase does not run (no results, so the run fails); `run-suite.sh` removes the file after the driver too, in case the driver was stopped by its timeout, and fails the phase if it is still there. The `tls.insecure` test is in group `grpc` (`-AllowFail grpc` covers it, as for the other gRPC tests); `-Only policy` together with `-SkipUi` or `-SkipPolicy` runs nothing and fails the run. Two mutations make the phase's tests fail: `no-policy-file` and `allow-list-in-settings` (the same allow list as a user setting: zig-stdio stays blocked, but `tls.insecure` is only warned about, because only an allow list defined by policy denies it).

Not covered: a URL-mode elicitation in chat (its "Host:" line and IDN warning) and the "Continue" prompt of a URL asked for again (the fault proxy asks once per call), sampling with tools, the gateway session of a Copilot CLI chat (`startMcpGateway(Uri)`), gRPC through a CONNECT proxy, and keepalive.

## The chat participant (`@e2e`)

The E2E extension registers the chat participant `@e2e` (`extension/src/chatParticipant.ts`; stable API `vscode.chat.createChatParticipant`, contribution `chatParticipants` with the id `mcp-e2e.e2e`), so MCP tool calls can be made from the chat view of this build without a Copilot sign-in. Every tool call it makes passes the request's `toolInvocationToken` to `vscode.lm.invokeTool`, so the chat view shows it as a tool invocation of that request. The grammar (the command is the slash command, or else the first word of the prompt):

| Request | What it does |
| --- | --- |
| `@e2e /call <server> <tool> [<JSON object>]` | Calls one MCP tool of the server directly with `vscode.lm.invokeTool` (no model; deterministic) and answers with the tool's result as text. Without the JSON the input is `{}`. Example: `@e2e /call zig-stdio greet {"name": "Ada"}`. |
| `@e2e /ask [<server>] <task>` | Runs the llama agent loop (`agent.ts`, model `llamacpp/qwen3-8b`) on the task with the tools referenced with `#` in the request, or else every MCP tool of `<server>`; the model picks the calls and the answer is the model's. Example: `@e2e /ask zig-grpc-tunnel Call the tool named greet with name set to "Grace" and tell me what it returned.` |
| `@e2e /tools <server>` | Lists the MCP tool names of the server (the names `/call` takes). |
| anything else | Shows this usage. |

`<server>` is a label of `config/servers.json`; a server without tools yet is started first. The chat view needs a model for the request: open it with `workbench.action.chat.open` and `{ query, isPartialQuery: true, mode: 'ask', modelSelector: { vendor: 'llamacpp', id: 'qwen3-8b' } }`, then run `workbench.action.chat.submit` (submitting through `chat.open` waits for a default chat agent, which needs a Copilot sign-in). Every request the participant handled is appended to `chat-requests.jsonl` of the suite's results (command, prompt, model, whether it carried a `toolInvocationToken`, each call with its input and result text, the answer or the error) and returned in the `ChatResult` metadata. The UI suite sends its chat requests the same way (without waiting for the submit command, since a request may wait for input in the chat) and waits for the participant's line in `ui\chat-requests.jsonl`; a finished response folds its tool invocation into "Completed <n> steps", which the driver expands before a screenshot.

## Expectation flags

A skip counts as success in the summary, so a test that skips for a missing feature would hide a regression on a build that has the feature. `run-suite.sh` therefore computes from the installed commit what the build is expected to support (`provenance.json`, `expect`): `MCP_E2E_EXPECT_GATEWAY_GRPC` and `MCP_E2E_EXPECT_GATEWAY_RATE_LIMITS` are `0` when the installed commit is `6201d830320` (the m8 package) or one of its ancestors in the clone, and `1` otherwise, including when the clone does not know the commit (strict). A test that names a feature (`requires: 'gateway-grpc'`: the three gateway-over-gRPC tests and the agent test through the gateway's gRPC listener; `requires: 'gateway-rate-limits'`: the rate limit test) may skip only when the flag is `0`; with `1` its skip is a failure ("expected on this build ..., but the test skipped"). No other test skips.

## Notes

- **Expected failures on the current packages**: on a build without the gRPC transport (`mcp-2026/m4-conformance-client`) the `grpc` group fails (the servers stay in the Starting state); run with `-AllowFail grpc` to see the rest pass. The m8 package (`6201d830320`) fails the soak test, `binding: auto` (auto fell back to the typed service) and the gateway opt-in assertions, and skips the gateway-over-gRPC and rate limit tests (not expected there). The suite is written against the product changes of the second gRPC round (`binding: auto` speaks only the tunnel and names `"binding": "typed"` in its error; `startMcpGateway(chatSessionResource?, { grpc: true })` opens the gateway's gRPC listener per gateway; the gateway rate limits; the `GrpcChannel` no longer resets completed streams): until a package with all of them is installed, the tests of what is missing fail by design.
- **The `protocolVersion` pin**: the setting's description (`mcpConfiguration.ts`) says "A pinned revision the server rejects still falls back to negotiation", and the pin test (`zig-http-pin-legacy`) asserts exactly that: `initialize` with 2025-11-25 first, then `server/discover` and 2026-07-28. Earlier builds did not: the Streamable HTTP transport treated the 4xx answer to the rejected `initialize` as a reason to try the legacy SSE transport (`will attempt to fall back to legacy SSE`), whose GET failed, and the server ended in the error state. The product now does what the test expects: the zig server's 400 carries a 2026-07-28 error (-32020), which reaches the engine as the answer to the `initialize`, and a 4xx without one whose legacy SSE fallback fails too aborts the `initialize` (`and the fallback to legacy SSE failed`), so in both cases VS Code probes with `server/discover` and negotiates 2026-07-28. A build from before that change fails this test.
- **Soak background**: a `GrpcChannel` that resets every completed stream (RST_STREAM(NO_ERROR)) trips nghttp2's rapid-reset protection in any Node `http2` server, which ends the session with GOAWAY(INTERNAL_ERROR). That protection is a bucket of 1,000 resets refilled at 33 per second, so with the default it only trips when the calls come faster than 33/s; the zig server answers a gRPC call in about 40 ms on Linux (no TCP_NODELAY, a zig-sdk 0.5.2 defect, not a VS Code regression), so VS Code makes at most about 25 calls/s here and the default bucket would never run dry. The soak proxy therefore runs with `--rst-rate 0` (no refill): the session ends after 1,000 resets however slowly they come, so a channel that resets completed streams over a socket fails after about 1,000 calls (the m8 reset cannot be provoked over a socket, see "Mutation runs"). The details record the calls per second and the mean milliseconds per call (no threshold): builds from round S to r9 waited a fixed 100 ms grace window after every tool call to a server that announces `tools.listChanged` (about 9.8 calls/s against 45 on m8); since the fix the window applies only to calls made for a chat request. Checked locally against the proxy with a Node client that resets every completed stream: GOAWAY(INTERNAL_ERROR) after 1,017 calls with `--rst-rate 0`, none in 1,200 calls at 21 calls/s with the default.
- **Model choice**: only the agent tests and `@e2e /ask` depend on which tool the model picks; their prompts name the tool and the arguments, the gRPC and gateway ones offer five tools only, their assertions name the expected tool and the result it must return, and the details record every call the model made. Everything else calls `invokeTool` directly, so a different choice of the model cannot change its result.
- **A missing resource over Streamable HTTP**: the zig server answers a `resources/read` of an unknown URI with HTTP 400 and the JSON-RPC error -32602 in the body (zig-sdk maps -32700, -32600, -32602 and -32020 to -32022 to 400 and -32601 to 404, as the gateway does for its own errors). Builds up to `20b8b2f239d` delivered the body of a 4xx only for the codes `isRecognizedModernError` accepts (-32020, -32021, -32022, and -32601 with 404), so this answer became the transport error `400 status sending message to ...` and the read failed with `FileSystemError` `Unknown` instead of `FileNotFound` (run e2e-api-res-1, zig-http). Since then, once a server speaks 2026-07-28, a non-2xx answer whose body is a JSON-RPC 2.0 error is delivered as the server's answer (except 401/403, which belong to the authorization flow, and 408/429/502/503/504, which stay aborts the engine may retry; `8db48fcbae5`), so the test reads the missing resource on both zig-stdio and zig-http.
- Trust: the servers of the user-level `mcp.json` belong to a collection with `McpServerTrust.Kind.Trusted` (`installedMcpServersDiscovery.ts`), as do extension-provided ones, so no trust prompt shows; the suite starts them with `workbench.mcp.startServer <id> { waitForLiveTools }` (retried: right after startup the MCP service may not have created the server yet, and the command then does nothing).
- Storage is in memory while extension tests run, so the seeded auto-approve opt-in only applies to the UI suite; the API suite sets the context key `vscode.chat.tools.global.autoApprove.testMode`, as `extensions/vscode-api-tests` does.
- The launcher asks for confirmation inside WSL containers (`/proc/version` says Microsoft); `DONT_PROMPT_WSL_INSTALL=1` skips it. Without an OS keyring, VS Code asks how to store secrets; `--password-store=basic` avoids the modal dialog.
- Containers reach each other by name on `vscode-e2e-net` only; ports that `wslc` publishes are bound on the Windows side (`127.0.0.1:8080` reaches llama.cpp from Windows, not from another container).
- Cleanup: `wslc remove -f llama-e2e; wslc volume remove vscode-e2e-work; wslc network remove vscode-e2e-net`.

## Building the `.deb` (`containers/build-vscode.ps1`)

`build-vscode.sh` clones the branch from the read-only mount into the volume (later runs fetch and hard-reset the clone; ignored files such as `node_modules` stay), uses exactly the `.nvmrc` Node version (downloaded once, SHA-256 checked), runs `npm ci` only when a `package.json`/`package-lock.json`/`.npmrc`/`.nvmrc` blob changed, then `npm run download-builtin-extensions`, `npm run gulp vscode-linux-x64-min`, `vscode-linux-x64-prepare-deb` and `vscode-linux-x64-build-deb`. A warm build takes about 6 minutes, a fresh one about 10 (`npm ci` 4 minutes). Logs: `.build\e2e\logs\build-vscode-<run>.log` and `.timings.tsv`. The workarounds, all applied to the clone only:

1. The built-in Copilot extension is packaged with `build/.moduleignore`, which strips `@github/copilot/**`; the official build overlays the Copilot VSIX of a separate CI job. On `Copilot SDK directory not found` the script copies the `@github/copilot` files that `vsce ls` lists for the VSIX into `.build/extensions/copilot` and reruns only the packaging task (`<target>-ci`).
2. The OSS build has no Rust tunnel CLI (`bin/code-tunnel-oss`), so the deb dependency calculator skips files that do not exist; `code-oss tunnel` is not in the package.
3. Native modules are compiled with the Ubuntu 24.04 toolchain instead of the glibc 2.28 sysroot toolchain, so the computed `Depends:` differs from `build/linux/debian/dep-lists.ts`; the check warns instead of failing (fine for Ubuntu 24.04 targets).
4. The image clears `ELECTRON_SKIP_BINARY_DOWNLOAD` of its base. The build container peaks at about 11.5 GB; with less memory the script falls back to the non-minified `vscode-linux-x64`.
