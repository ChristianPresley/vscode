# Visual verification

The UI suite (`ui/visual.ts`) and the enterprise policy phase (`ui/policy.ts`, rows 27 to 27c) take these screenshots of the installed fork (1600x1000, under xvfb, Playwright `_electron.launch` of `/usr/share/code-oss/code-oss`) into `.build/visual-verification/`. Each row says what must be visible. `ui-results.json` (`policy-results.json` for 27 to 27c) of a run records, per screenshot, the automatic DOM checks of the driver (`checks`) and the text it read (`note`); `summary.md` lists them, and a screenshot whose checks fail, a screenshot section that throws, or a screenshot whose UI never shows fails the run (`runner/summarize.ts`; `-AllowFail visual` reports them as allowed failures instead). The verdicts below are from looking at the images.

Verdicts: **holds**, **does not hold** (with what is visible instead), **n/a** (cannot be shown by this build or this headless run, with the reason and the tests that cover the behaviour).

The verdicts were recorded on 2026-10-21 from the screenshots of two full UI runs. **`e2e-ui-final-1`** (`-SkipApi`, no `-Only`) tested `code-oss_1.144.0-1792614133_amd64.deb`, built from `e094cd4da20` of `mcp-2026/r10-tool-refresh-latency`, with the suite of the working tree; every DOM check of every screenshot passed there and in `e2e-ui-full-1` before it (which had every screenshot but 14b). **`verify-9064`** (API and UI, no `-Only`) tested `code-oss_1.144.0-1792629863_amd64.deb`, built from `9064b171a54`, which adds the product fixes `8db48fcbae5` (a 2026-07-28 HTTP answer with a JSON-RPC error body is delivered; a failed request no longer fails the connection), `6a7e76bb63d` (MCP Apps get the 2025-11-25 result shape) and `552c3f8164b` (the gateway logs each gRPC request), with the committed suite ("suite matches commit: yes"): API 109 of 109, UI 14 of 14, 45 of 45 screenshots, every check passed. Rows 18b and 22e and the M10 gateway log line were recorded on `verify-9064`; the rest hold in both runs (looked at again in `verify-9064` where a product fix could change them: 22e, 23 to 23c, 24g). Each run keeps its screenshots in `.build/e2e/runs/<run id>/screenshots/`. Rows 01 to 15 and 08b were first recorded on `final-e094-r3` and `vv-check-1`. Rows 26 and 26b and the URL consent row of M3 were recorded on **`url-2`** (`-SkipApi -Only url-elicitation`): `code-oss_1.144.0-1792635340_amd64.deb`, built from `24731b6d9b9` of `mcp-2026/r12-url-elicitation`, with the committed suite; both URL scenarios and both screenshots passed. On `url-1`, the package of `cdc35c5f77d` before that fix, the declined scenario failed (see the findings), and `mut-no-url-elicitation` on the package of `24731b6d9b9` failed both URL scenarios and both screenshots.

How the suite gets there without a Copilot sign-in: the tool calls in chat (22c to 24g) are requests to the E2E extension's chat participant `@e2e` (`extension/src/chatParticipant.ts`), typed into the chat view with Ask mode and the llama.cpp model (`workbench.action.chat.open` with `isPartialQuery`, then `workbench.action.chat.submit`). `@e2e /call <server> <tool> <JSON>` calls the tool with `vscode.lm.invokeTool` and the request's `toolInvocationToken`, so the chat view shows the call as a tool invocation of the request, with its elicitations in the chat, its progress and its errors. A chat request first starts the servers that never ran (`chat.mcp.autostart`), the OAuth ones included, so the chat sections run after the OAuth scenarios; the Accounts menu (25) comes right after the zig-oauth sign-in, before the other sign-ins, whose accounts would have the same label.

The configuration of a run has 30 servers (`config/servers.json`): 27 in the user `mcp.json` and three API definitions of the E2E extension (zig-grpc-api, zig-grpc-api-typed, zig-grpc-api-tls). Lists of that length scroll, so an image shows one part of the list and the DOM checks read all of it. Two sections change state and undo it: 21 sets `chat.mcp.deniedServers` in the user `settings.json` and restores the file, and 25b signs out of the zig-oauth account (its scenario has passed by then). Nothing writes an `mcp.json`: the completions edit the open file without saving, and 19b cancels at the destination picker (its check compares both `mcp.json` files before and after). The policy phase (27 to 27c) has its own user data folder, whose `mcp.json` it reduces to zig-http, zig-stdio and zig-grpcs-insecure before VS Code starts, and its policy file exists only while its window runs.

## Findings

Open:

- **The OAuth consent lists no scopes** (M5): "The MCP Server Definition '<label>' wants to authenticate to <resource name>." (15, `mainThreadMcp.ts` `loginPrompt`) names the server and the protected resource; the plan asked for the requested scopes too.
- **A missing resource over Streamable HTTP was not FileNotFound** on `e094cd4da20` (22e): the zig server answers `resources/read` of an unknown URI with HTTP 400 and -32602 in the body; that package delivered a 4xx body as the JSON-RPC error only for the codes `isRecognizedModernError` accepted, so the editor showed "unexpected error" (`e2e-ui-final-1`). Fixed by `8db48fcbae5`: once the server speaks 2026-07-28, a non-2xx answer whose body is a JSON-RPC 2.0 error is delivered as the server's answer (not 401/403, which belong to the authorization flow, nor 408/429/502/503/504, which stay aborts the engine may retry). 22e and the zig-http API test hold on `9064b171a54` (`verify-9064`).
- **The gRPC configuration form is unreachable** (19c): the MCP server detail of Agent Customizations shows the form (`embeddedMcpServerDetail.ts` `resolveSourceFormInput`) only for servers of the files shared with other clients (a workspace `.mcp.json`, Copilot's `mcp-config.json`); those files cannot hold gRPC servers (`getUnsupportedMcpServerConfigurationMessage`, `getWorkspaceRootMcpConfigurationError`), and the form offers grpc only for VS Code's own `mcp.json` format (`getMcpServerFormCapabilities`). So no product surface shows the gRPC fields (binding, TLS) or their accessible labels; a gRPC server's detail is read-only with "Edit Configuration".
- **No per-request route line in the gateway log** of packages before `552c3f8164b` (M10); since then each gateway gRPC request is logged at debug with its route, binding, method or RPC and outcome (`verify-9064`).
- **The gateway log is not captured by the UI suite**: a control route (or UI scenario) of the E2E extension that calls `vscode.lm.startMcpGateway(undefined, { grpc: true })` in the UI window (`extension/src/control.ts`) would let a screenshot show the "MCP Gateway" output with the `grpc://` advertisement and, on a package with it, the per-request line.

Observations (upstream behaviour, not changes of this fork):

- A finished tool invocation that reported progress keeps its last progress message as its label (24b: "Round 1: answered 3 input request(s)", 24d) instead of "Ran <tool>".
- Errors of MCP requests read "MPC -32020: ..." in chat (23c): the message prefix of `MpcResponseError` in `mcpTypes.ts` since the first MCP commit.
- Elicitation enum pickers label each option by its value and show the title as its description (14b).

## Findings from earlier packages (fixed)

- **A declined elicitation left its notification open** on `cdc35c5f77d` (`url-1`, the declined URL scenario): outside chat, Cancel and Decline are secondary actions (More Actions...), which do not close a notification by themselves, and neither did a cancelled call. The notification stayed with its primary button live, so after a declined URL elicitation Open URL still opened the URL. The decline itself was right on the wire: the retry with `decline` went out 0.8 s after the round. But the toast stayed, and the driver chose Cancel three times. Fixed in `24731b6d9b9`: the form, consent and URL notifications close once the elicitation is answered (unit tests in `mcpElicitationService.test.ts`). `url-2` passes.
- **gRPC servers stayed "Starting"** on the m4 package (02, 05), which had no gRPC transport. Gone with the transport (m8 on); since `3ee90968730` a start that throws goes to Error.
- **The typed binding named its server after the address** (m8, 05): fixed in `f589de6f3ef`; 05 checks "mcp-conformance-test-server zig-grpc-typed".
- **No schema for the user-level mcp.json** (m8, 08): fixed in `3ee90968730`; 08b checks it.
- **Tool titles not shown** (m4, m8, 05b): fixed in `3ee90968730`; 05b checks it.
