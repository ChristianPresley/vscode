# Visual verification

The UI suite (`ui/visual.ts`) takes these screenshots of the installed fork (1600x1000, under xvfb, Playwright `_electron.launch` of `/usr/share/code-oss/code-oss`) into `.build/visual-verification/`. Each row says what must be visible. `ui-results.json` of a run records, per screenshot, the automatic DOM checks of the driver (`checks`) and the text it read (`note`); `summary.md` lists them, and a screenshot whose checks fail, a screenshot section that throws, or a screenshot whose UI never shows fails the run (`runner/summarize.ts`; `-AllowFail visual` reports them as allowed failures instead). The verdicts below are from looking at the images.

Verdicts: **holds**, **does not hold** (with what is visible instead), **n/a** (cannot be shown by this build or these servers). They were recorded on 2026-10-20 for two packages:

- **m4**: `code-oss_1.144.0-1792513451_amd64.deb`, branch `mcp-2026/m4-conformance-client`, commit `52071c6ff1a` (gRPC configuration and API, no gRPC transport); runs `n2-run1`, `n2-run2`, `n2-run3`. Every automatic check passed in all three runs.
- **m8**: `code-oss_1.144.0-1792520798_amd64.deb`, branch `mcp-2026/m8-grpc-transport`, commit `6201d830320` (with the gRPC transport); runs `n2-m8` and `n2-m8-final`, and with the stricter checks `n3-run1`, `n3-run2`, `n3-run3` (every screenshot check passed; 12 re-checked by eye in n3-run3). The images now in `.build/visual-verification/` are from the latest m8 run; each run also keeps its own copy in `.build/e2e/runs/<run id>/screenshots/` (runs from n2-m8-final on).

The verdicts are the same for both packages except where a row says otherwise. The checks of 01, 02, 05 and 05b were made stricter in round three (T2: per-server states, the typed serverInfo name) and the configuration has more servers since; those rows say what the new checks expect, and their verdicts wait for the first container run with them.

## Findings from the screenshots

- **gRPC servers stay "Starting"** on the m4 package (02, 05): the extension host's `_startMcp` throws `not implemented` for the gRPC launch (renderer log: `Error: not implemented at xD._startMcp ... $startMcp`), `$startMcp` is a fire-and-forget call, so the server's connection never reaches Error; its MCP log ends with `Connection state: Starting`, and `workbench.mcp.startServer <id> { waitForLiveTools: true }` never resolves. Expected to go away with the gRPC transport; a failing `$startMcp` should still surface as an Error state.
- **The typed binding names its server after the address** (m8, 05): the synthesized `server/discover` of `binding: typed` reports `serverInfo` `{"name":"127.0.0.1:50052","version":""}` (MCP log of zig-grpc-typed), although every typed response that follows carries `_meta.serverInfo` `{"name":"mcp-conformance-test-server","version":"0.1.0"}`. The tools picker shows "127.0.0.1:50052" and the tool ids get the prefix `mcp_127_0_0_1_500_`.
- **No schema for the user-level mcp.json** (08): `extensions/configuration-editing/package.json` associates `vscode://schemas/mcp` with `/.vscode/mcp.json` only, so `<user data>/User/mcp.json` (which "MCP: Open User Configuration" lists as "VS Code User Configuration - Legacy", next to the recommended Copilot CLI `~/.copilot/mcp-config.json`) gets word completions and no validation of `"type": "grpc"` or `binding`. This holds for the package built from commit `6201d830320` only: it is reported as a product bug, so re-check 08 in the user-level file on a package built after the fix (the screenshot keeps using the workspace `.vscode/mcp.json`).
- **Display names**: neither the server editor (03, 04: Configuration tab only) nor the tools picker (05b: `toolReferenceName ?? displayName`) shows tool titles; serverInfo names show in the tools picker (05) only.
- The installed-servers view (01) shows no connection state; MCP: List Servers (02) does.
- With only `"type": ""` in a new server, the JSON completion of `type` offered only "stdio" in a trial run; with a `grpc://` url it offers "grpc" (08), so the screenshot uses that.
